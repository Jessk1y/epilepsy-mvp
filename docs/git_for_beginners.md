# Git для новичков: как работать в команде

Главная идея: **в `main` никто не пишет напрямую.** Работаем в своей ветке, потом открываем pull request (PR), его смотрит другой человек, и только после этого ветка вливается в `main`.

## Один раз на каждой машине

```bash
git clone https://github.com/Jessk1y/epilepsy-mvp.git
cd epilepsy-mvp
git config user.name "Имя Фамилия"          # локально, без --global
git config user.email "ваша@почта"
git config core.hooksPath .githooks         # включает проверку «нет данных и весов в коммите»
```

## Каждый эксперимент

```bash
git checkout main
git pull                                    # 1. забрать свежее
git checkout -b h1/zs/deepepilepsy-turkish  # 2. своя ветка: гипотеза/автор/тема
# ... работаете, копируете templates/experiment_template.ipynb в h1_eeg/notebooks/ под новым именем ...
git status                                  # 3. посмотреть, что изменилось
git add h1_eeg/notebooks/<ваш_блокнот>.ipynb experiments_log.md
git commit -m "Г1: DeepEpilepsy на турецком наборе, ROC AUC 0,xx"
git push -u origin h1/zs/deepepilepsy-turkish
```

4. На GitHub нажмите «Compare & pull request», заполните чек-лист, в «Reviewers» выберите коллегу.
5. Ревьюер читает блокнот (смотрит шапку, деление по пациентам, метрики, выводы) и пишет комментарии или нажимает «Approve».
6. После одобрения автор нажимает **Squash and merge**, затем удаляет ветку.
7. Вернуться на `main`: `git checkout main && git pull`.

Что смотрит ревьюер: нет данных и весов; деление по пациентам; выводы сохранены; метрика на уровне пациента; вывод соответствует цифрам (не завышен); журнал заполнен.

## Как не ловить конфликты в .ipynb

Блокнот — это JSON с выводами, и два человека, правящие один файл, почти гарантированно получат конфликт. Поэтому:

1. **Один блокнот — один автор.** Чужие блокноты не редактируем (см. `naming_and_journal.md`).
2. **Новый эксперимент — новый файл.** Не переписываем старый блокнот, а копируем.
3. **Короткие ветки.** Влили PR — удалили ветку, следующую начинаем от свежего `main`.
4. **Общие файлы** (`experiments_log.md`, `SUMMARY.md`, `common/`) — правим малыми кусками и сразу вливаем; перед правкой `git pull`.
5. Перед коммитом: **Restart kernel and Run All**, чтобы номера ячеек не прыгали; не коммитьте «в процессе».
6. Не открывайте один и тот же блокнот одновременно на Kaggle и локально, а потом оба сохраняя: выберите одно место и скачайте итог.
7. Код, нужный нескольким людям, переносите из блокнота в `common/` или `h?_*/src/` — так он живёт в обычных `.py`, где git конфликты разбирает нормально.

Если конфликт всё же случился:

```bash
git status                       # какие файлы в конфликте
```

- в `.py` / `.md` — откройте файл, найдите `<<<<<<<`, `=======`, `>>>>>>>`, оставьте нужное, удалите маркеры, `git add файл`, `git commit`;
- в `.ipynb` — **не правьте руками**. Возьмите свою версию: `git checkout --ours <файл>` (при слиянии `main` в вашу ветку) или версию из `main`: `git checkout --theirs <файл>`, и при необходимости перезапустите блокнот. Если не уверены — напишите в чат команды, ничего не стирая;
- необязательно удобнее: `nbdime` (`py -m pip install nbdime`, затем `nbdime config-git --enable`) — показывает различия блокнотов по ячейкам. Установка на ваше усмотрение.

## Чего не делать
- `git add .` и `git add -A` вслепую: сначала `git status`, добавляйте файлы по имени;
- `git push --force`;
- коммитить данные, веса, ключи, `kaggle.json`, токены. Если случайно закоммитили — **не пушьте**, напишите команде; если уже запушили — сообщите сразу, историю придётся чистить;
- работать в `main`.
